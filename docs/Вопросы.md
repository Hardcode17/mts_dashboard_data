3. ITSC и координатор: дубли инцидентов и два источника правды

4. Есть ITSC и координатор со своей системой. Может ли случиться такая ситуация:

- ITSC присылает инцидент 1;
- координатор ставит на него ответственного;
- в процессе ITSC присылает инцидент 1 ещё раз: в нём либо нет ответственного, либо он есть, но другой (кто-то назначил его на стороне ITSC);
- в результате получаем два источника правды.

Мнение: не нужно выдумывать механизм типа мёрджа. Должен быть единый источник правды. Пока инцидент находится у координатора, повторная его отправка должна блокироваться ещё на уровне ITSC. Но вопрос надо зафиксировать.

**Принятое решение (21 ноября 2026):**
Из нашего дашборда **можно менять инциденты** (назначать ответственного, менять статус и менять группу). Чтобы не возникало двух расходящихся источников правды, дашборд изменяет инцидент синхронно во внешней ITSM (`itsm-mock`) через наш бэкенд по **5. Общему контракту**:

| Действие | Метод | Endpoint |
| --- | --- | --- |
| Получить список инцидентов | `GET` | `/itsm_incident` |
| Получить инцидент по ID | `GET` | `/itsm_incident/{sys_id}` |
| Получить список пользователей | `GET` | `/user` |
| Назначить ответственного | `PATCH` | `/itsm_incident/{sys_id}` |
| Изменить статус | `PATCH` | `/itsm_incident/{sys_id}` |
| Изменить группу | `PATCH` | `/itsm_incident/{sys_id}` |

После `PATCH /itsm_incident/{sys_id}` обновлённые данные сразу сохраняются в `itsm-mock` (`SnapshotStore`) и в БД бэкенда с записью в журнал аудита, поэтому следующий 30-секундный снимок от `itsm-mock` приходит уже с теми же актуальными значениями и не перетирает изменения координатора. [`docs/itsm-mock-contract.md`](itsm-mock-contract.md)).
