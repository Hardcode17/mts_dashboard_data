Прогноз нарушения срока

Оценка риска того, что инцидент не будет решён до дедлайна. Без ML-сервиса, без LLM и без нового микросервиса: модель — это логистическая регрессия, то есть взвешенная сумма нескольких признаков и порог. Коэффициенты обучаются офлайн на реальных исторических данных, а в продукт попадают как константы в существующий Spring Boot бэкенд.

Отдельная ветка KAN-46 «Оповестить о приближении срока» не входит в этот сценарий: оценка риска не заменяет дедлайн, не меняет приоритет и не дублирует предупреждение по остатку времени. Согласуется с проверкой прогноза на истории: в обучение попадают только случаи с известным сроком, признаки — только из данных, доступных на момент прогноза.

Идея и границы

ВопросРешение
Что предсказываемКатегорию риска нарушения дедлайна для активного инцидента: низкий / средний / высокий. Не вероятность, не новый дедлайн.
Какая модельЛогистическая регрессия: score = w0 + Σ wi·xi, пороги на категории. «Скорость исполнителя + приоритет + дедлайн + похожие задачи + веса» — это она и есть, в явном виде.
Где живёт в продуктеОдин Java-класс в существующем бэкенде. В рантайме — сложение и умножение, ноль зависимостей, размер модели — несколько констант.
Кто решаетКоординатор. Оценка не меняет дедлайн, приоритет и статус в ITSM.
Что не делаемНе обучаем модель в рантайме, не заводим Python-сервис, не показываем проценты как «вероятность», не смешиваем с предупреждением по остатку времени (KAN-46).

Признаки и модель

Признаки вычисляются на момент оценки t. Целевая переменная — made_sla (для адаптированных данных — «completionDate позже псевдо-дедлайна»).

x2 — дедлайн уже продлевался (да/нет или число раз к моменту t)сильный сигнал из incident_deadline_changes
x3 — число переназначений группы/исполнителя к моменту t«болтание» карточки

x7 — приоритет UCI (1 — Critical, 4 — Low)учитываем корреляцию с дедлайном: сначала проверяем на истории, что не считаем одно и то же дважды

Обучение (офлайн, KAN-81). Python-ноутбук: логистическая регрессия из sklearn, разбиение строго по времени (обучение на ранних инцидентах, проверка на поздних). Метрики: полнота пойманных просрочек, доля ложных срабатываний, за сколько времени до дедлайна предупреждает. Обязательное сравнение с бейзлайнами: «осталось < N часов» и медиана по сервис × приоритет × группа. Правило решения: если регрессия не бьёт медианный бейзлайн заметно — в продукт идёт бейзлайн.

Веса после обучения (результат KAN-81: UCI 498, 23 323 инцидента с известным решением, разбиение по времени 70/30, seed 42):

метрики на отложенной выборке (7 122 оценки)recall просрочек 0.918, precision 0.662, F1 0.769, ложные срабатывания 0.151; lead time: медиана −91 ч, т.е. 84% срабатываний случаются уже после дедлайна (следствие протокола «t равномерно в открытие→решение»), среди сработавших заранее — за 13 ч до дедлайна. На подвыборке «оценка ещё до дедлайна»: recall 0.636, precision 0.295, F1 0.403

Экспериментальный итог: регрессия не бьёт бейзлайны заметно — фиксируем честно. Бейзлайн A «до дедлайна < 33 ч» (порог N подобран на train под тот же бюджет): recall 0.925, precision 0.671, F1 0.778 при 14.6% ложных срабатываний — лучший результат из всех. Бейзлайн B с множителем (медиана × 0.50 > остатка): recall 0.922, F1 0.715 при 21.2% ложных. Регрессия (recall 0.918, F1 0.769) формально обходит B по F1, но не добирает ни +5 п.п. recall, ни превосходства над A. На подвыборке «оценка до дедлайна» картина та же: A — F1 0.427, регрессия — 0.403, B tuned — 0.325. Главный сигнал в этих данных — сам остаток времени до дедлайна.

Продуктовое решение (22 ноября 2026): дефолтный режим в KAN-82 — регрессия. Разница с порогом копеечная (F1 0.769 против 0.778 на UCI), зато регрессия оценивает комбинацию факторов — переназначения, застревание в статусе, нагрузку исполнителя, продления — и способна поднять «Высокий риск» заранее, а не только по остатку часов; основания оценки при этом содержательнее. Пороговый режим «остаток < N часов» (N пересчитывается на реальной истории МТС) остаётся запасным переключателем в конфиге. При появлении реальной истории МТС: переобучить веса скриптом tools/train_deadline_risk.py и сравнить режимы ещё раз — Java-скоринг воспроизводит веса по tools/deadline_risk_weights.json без стандартизации (клампы признаков зафиксированы там же), замена — правка конфига.

Обучение и эксплуатация разделены:

                                              double score(features)

  • Скоринг вызывается в существующем фоновом контуре при публикации снапшота ITSM (ItsmSnapshotPublished) — для активных инцидентов с дедлайном; отдельной очереди и pgvector не нужно.

  • В карточке — категория и список оснований с числами. Оценка не меняет дедлайн и приоритет.

Контракт API (KAN-82 → KAN-83)

Риск отдаётся в составе существующей карточки инцидента, отдельный микросервис не заводится.

"deadlineRisk": {
  "risk": "high",              // low | medium | high | unknown
  "evaluatedAt": "2026-11-21T10:00:00Z",
  "reasons": [
    { "code": "group_median_exceeds",
      "text": "Медиана группы решения 6.0 ч, до дедлайна 2.1 ч" },
    { "code": "deadline_extended",
      "text": "Дедлайн уже продлевался 1 раз" }
  ],
  "score": 0.83                // только для отладки, в UI не показывать
}
  • risk: unknown — нет дедлайна, данных группы или оценка недоступна; карточку не блокирует.
  • reasons — человекочитаемые основания с числами; score наружу не интерпретировать как вероятность.
  • Фронт: бейдж с цветовой кодировкой по существующей палитре, раскрывающийся список оснований, состояния «риск неизвестен» и «анализ недоступен». Предупреждение о приближении срока (KAN-46) отображается рядом, но отдельно.
