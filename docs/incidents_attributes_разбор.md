# `incidents_attributes.json` — описание атрибутов

**Назначение:** словарь **30 полей**, а не сам набор инцидентов и не строгая JSON Schema. Каждая запись содержит `api_source` (имя поля), `description` (словесное объяснение) и `possible_values` (пример/перечень значений). У некоторых полей `possible_values` — пустая строка.

**Данные для примеров:** значения из `character_problems.json` (44 инцидента, 46 полей в каждом). Неописанных в словаре полей — **16**; их разбор во втором файле.

## Структура самого файла-словаря

| Ключ в объекте словаря | Что хранит | Пример |
|---|---|---|
| `api_source` | Имя поля в инциденте | `priorityId` |
| `description` | Его описание | `Приоритет инцидента...` |
| `possible_values` | Пример или перечисление значений; иногда пусто | `1, 2, 3, 4` |

## Формально заявленные значения и что наблюдается

| Поля | Заявлено в словаре | Подтверждено выгрузкой |
|---|---|---|
| `stateId`, `state` | `0` Назначен, `2` Выполняется, **`7` Закрыт, `10` Завершен** | `0` Назначен, `2` Выполняется, **`7` Завершен, `10` Закрыт, `20` Исследование ситуации** |
| `priorityId` | `1..4` | `1` Низкий, `2` Средний, `3` Высокий; `4` в данном срезе нет |
| `impactId`, `urgencyId` | `1..4` | `impactId`: 2/3/4; `urgencyId`: 1/2/3/4 |
| `submitDate`, `completionDate`, `deadline` | `YYYY-MM-DD HH:MM:SS` | ISO 8601: `2026-11-08T12:02:29Z`, иногда дробные секунды, `null` для отсутствующих дат |
| `isNeedUp` | «Да», «Нет» | `true`, `false`, `null` (JSON boolean / null) |
| `impact`, `urgency` | Перечислены формы «Наивысший, ...» | Реальные формы: `Наивысшее` для влияния, `Наивысшая` для срочности |
| `serviceType` | Клиентский / Пользовательский / Технологический (с опечатками) | Те же категории, нормальные написания |

## Подтверждено экспертами МТС (переписка 20.11.2026)

- **`7 = Завершен (Resolved)`** — проблема устранена, но инцидент **можно вернуть в работу**, если она осталась или решение не помогло.
- **`10 = Закрыт (Closed)`** — работа окончательно закончена; вернуть этот инцидент в работу нельзя. При повторном сбое создают **новый инцидент**.
- **Первоначальный ответ по `solution`:** поле может содержать предыдущую неудачную попытку устранения даже до `Resolved`.
- **Последующее уточнение:** при `state` = «Назначен» или «Выполняется» поле `solution` **не должно быть заполнено**. Эти два разъяснения **противоречат друг другу**. В рабочей логике используем последнее уточнение, но окончательно вопрос стоит согласовать.
- Файл с инцидентами — **мини-выгрузка состояния на момент времени, начальная база**; важно видеть существенные изменения полей (статуса, команды и др.). Импорт, БД и API — **выбор команды**, а не предписанная организаторами схема.

## Что ещё стоит уточнить

1. Есть ли официальный полный справочник статусов (включая `Research = 20`), допустимые переходы и правила SLA для исследования?
2. Что означает `completionDate` при `stateId = 20`: окончание технического сбоя или формальное закрытие?
3. Рассчитывается ли `priorityId` по фиксированной матрице `impactId × urgencyId` или может быть изменён вручную?
4. Уточните окончательное правило для `solution`: допускается ли текст предыдущего неудачного решения при статусах `Назначен` / `Выполняется`? Как представлять незаполненное поле — `null`, `""` или иначе?
5. Можно ли получить полную документацию по 16 дополнительным полям (особенно ссылкам на связи между инцидентами и `isRootIncident`)?
5. Окончательно уточнить правило `solution`: могут ли активные инциденты хранить описание **предыдущих попыток**, или при `Assigned`/`WorkInProgress` поле всегда должно быть пустым?

**Практический вывод:** использовать справочник как подсказку о смысле полей, но при конфликте с выгрузкой опираться на фактический формат и уточнения экспертов. Для активных инцидентов `solution` считать **аномальным заполнением** по последнему уточнению; не считать его признаком завершения. **Не переписывать исходный JSON молча**: при необходимости фильтровать поле на уровне представления или анализа, а расхождение фиксировать. Не валидировать объекты только по `possible_values`: это не полноценная схема.
