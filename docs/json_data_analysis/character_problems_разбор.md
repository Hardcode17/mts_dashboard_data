# `character_problems.json` — актуальный разбор выгрузки инцидентов

## Назначение и договорённости

Это **пример начального снимка состояния инцидентов**, а не журнал их изменений: массив из **44 объектов**, каждый содержит **46 полей**. Поля и тестовые значения разрешено корректировать, добавлять новые; при этом следует сохранять базовый набор данных, необходимый для дашборда. Импорт, экспорт, хранение в БД и способы доставки обновлений — на усмотрение команды. **Существенные изменения инцидентов должны отражаться в интерфейсе автоматически.**

В таблицах **†** отмечены **16 полей**, отсутствующих в отдельном словаре `incidents_attributes.json`. Типы отражают **фактический исходный JSON**; при разработке модели допустимо предусмотреть `null` там, где это нужно по принятой бизнес-логике. Примеры строк независимы и могут происходить из разных инцидентов.

### Актуальный справочник статусов

| `stateId` | `stateEnum` | `state` | Записей | Правило |
|---:|---|---|---:|---|
| `0` | `Assigned` | Назначен | 14 | Инцидент назначен, требуется работа |
| `2` | `WorkInProgress` | Выполняется | 10 | Ведётся работа над проблемой |
| `7` | `Resolved` | Завершен | 10 | Проблема устранена, **возможен возврат в работу** |
| `10` | `Closed` | Закрыт | 5 | Работа окончательно завершена, **возврат невозможен**; повторный сбой — **новый инцидент** |
| `20` | `Research` | Исследование ситуации | 5 | Проблема устранена, продолжается анализ причин; возможна передача между командами |

**Важно:** словарь `incidents_attributes.json` содержит устаревшую перестановку кодов `7`/`10` и не описывает `20`. Здесь зафиксировано **актуальное** соответствие по выгрузке и разъяснениям экспертов. Конкретную полную матрицу переходов команда может определить в своей реализации.

## 3. Даты и SLA

| Поле | Тип | Назначение | Пример |
|---|---|---|---|
| `submitDate` | `string` | Время регистрации инцидента | `2026-11-08T12:02:29Z` |
| `deadline` | `string / null` | Крайний срок решения | `2026-11-22T12:02:29Z` |
| `completionDate` | `string / null` | **Время перевода инцидента в статус `7 = Завершен (Resolved)`** | `2026-11-08T04:01:31Z` |
| `lastAssignmentToTeamDateTime` † | `string / null` | Время последнего назначения команде | `2026-11-11T12:30:36Z` |
| `waitingExitDate` † | `string` | Служебное время выхода из ожидания; в примере только заглушка | `0001-01-01T00:00:00` |

**Как трактовать `completionDate`:** поле фиксирует событие **перехода в `Resolved`**, а **не момент перехода в `Closed`**. Поэтому наличие `completionDate` у записей со статусами `Research` и `Closed` нормально: инцидент ранее уже достиг `Resolved`. Во входном снимке `completionDate = null` у всех 24 инцидентов в статусах `0` и `2`.

Формат реальных временных полей — ISO 8601, UTC (`Z`), иногда с дробными секундами. При `deadline = null` оставшееся время до SLA не вычисляется. Значение `waitingExitDate = 0001-01-01T00:00:00` трактуем как техническую заглушку, а не реальную дату.

## 5. Текст проблемы и решения

| Поле | Тип в выгрузке | Назначение | Пример |
|---|---|---|---|
| `header` | `string` | Заголовок инцидента | `Отказ Объектив (Камера-сканер)` |
| `description` | `string` | Полное описание проблемы | `Автоматический алерт: Объектив ...` |
| `shortDescription` † | `string` | Краткое описание проблемы | `Зафиксировано отклонение в работе Объектив.` |
| `solution` | `string` | Описание решения инцидента | `Отрегулирован Объектив, инцидент закрыт.` |

**Принятое правило:** при `stateId = 0` (**Назначен**) или `2` (**Выполняется**) поле `solution` должно быть **пустым** (`null` либо пустая строка — по принятой схеме). **В примере нарушено правило у всех 24 таких записей; это ошибка тестовых данных**, а не повод менять бизнес-правило.

Пример из исходной выгрузки (некорректный):

```json
{
  "id": "INC000021931151",
  "stateId": 0,
  "state": "Назначен",
  "completionDate": null,
  "solution": "Отрегулирован Объектив, инцидент закрыт."
}
```

**Корректный вариант для нашей модели:** `"solution": null` (либо `""` при выбранном строковом контракте). Текст из исходной выгрузки не используем как доказательство устранения проблемы.

## 9. Правила интеграции для проекта

1. **Импорт и обновление:** использовать `id` как уникальный ключ инцидента. При повторном получении снимка выполнять обновление существующих записей, а не слепую вставку дублей.
2. **Автоматические изменения:** отслеживать новые `id`, изменение `stateId`, `priorityId`, `assignedGroupName`, `deadline` и других значимых полей. Повторное получение того же снимка не создаёт повторных оповещений.
3. **Группы дашборда:** критические (`priorityId = 4`, статус `0` или `2`); высокие (`priorityId = 3`, статус `0` или `2`); на координаторах (`assignedGroupName` совпадает и статус требует действий — `0`, `2` или `20`); исследование (`stateId = 20`). Один инцидент может попадать в несколько групп.
4. **Завершение и закрытие:** `Resolved (7)` допускает возврат; `Closed (10)` окончательный; `completionDate` обозначает время перехода в `Resolved`.
5. **Коррекция примера:** при импорте допускается нормализовать `solution` для `stateId = 0`/`2` либо сохранить оригинальный снимок отдельно и показывать очищенную доменную модель. Не выдавать некорректное значение за фактически выполненное решение.
6. **Приоритет и сроки:** использовать готовый `priorityId`; `deadline = null` отображать как отсутствие срока. Приоритеты и допустимые переходы можно определить в собственных бизнес-правилах, не нарушая обязательные сценарии кейса.
7. **Расширение формата:** добавлять поля и менять тестовые значения разрешено; для совместимости сохранить базовый набор атрибутов и функции импорта/экспорта.
