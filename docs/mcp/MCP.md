# MCP Dashboard — контракт v1 (KAN-77)

Редакция 1.0.0 от 22 ноября 2026, подготовлена для ревью backend и клиентов.
Это спецификация будущего адаптера, не отчёт о готовности сервера или согласовании команды.

Основание: [KAN-76](https://sokolenkonikita12ru.atlassian.net/browse/KAN-76),
[KAN-77](https://sokolenkonikita12ru.atlassian.net/browse/KAN-77),
[KAN-74 / Co-Coordinator](../co-coordinator.md).
Ранее указанный в Jira `docs/mcp/MCP.md` отсутствует в доступных ветках
Hardcode17/mts_dashboard_data на коммите `f21eee8`. Этот документ создан по требованиям
Jira и проверенному коду Hardcode17/mts_dashboard_backend (`f0acbe9`), а не восстановлен
из недоступного оригинала. Новые решения ниже требуют ревью перед реализацией.

## Артефакты и версия

- [contract.schema.json](v1/contract.schema.json) — JSON Schema 2020-12: общие типы и 12 схем входа/выхода.
- [examples.json](v1/examples.json) — шесть синтетических пар запрос/ответ.
- [build_contract.py](v1/build_contract.py) — источник генерации этих двух файлов.
- [test_contract.py](v1/test_contract.py) — проверка схем, примеров, отрицательных случаев и воспроизводимости генерации.

Для инструмента `X` вход задаёт `$defs.XInput`, выход — `$defs.XOutput`.
При регистрации инструментов адаптер помещает соответствующую схему и общие `$defs`
в самостоятельный `inputSchema`/`outputSchema`; внешних HTTP-ссылок для разрешения типов нет.
Обязательные поля, enum и семантика зафиксированы. Несовместимые изменения требуют v2;
новые инструменты можно добавлять отдельно. Клиент v1 не должен отправлять неизвестные поля.

По [спецификации MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)
результат возвращается в `structuredContent`, а его JSON-копия — в текстовом блоке `content`.
`ok=false` сопровождается `isError=true`; при успехе `isError=false`.
Неизвестный инструмент/невалидный JSON-RPC остаётся ошибкой протокола; прикладные ошибки
имеют типизированный объект `error`. Схема описывает именно `structuredContent`.

## Объём пилота

| Инструмент | Когда нужен | Назначение |
|---|---|---|
| `list_incidents` | Минимальный удалённый пилот | Ограниченная выдача опубликованных INC |
| `get_incident` | Минимальный удалённый пилот | Карточка по точному ID |
| `list_incident_changes` | Фоновый пилот | Replay общего журнала KAN-28 |
| `find_similar_incidents` | Рекомендация группы | Завершённые аналоги, точные коды и PostgreSQL FTS |
| `find_resolver_groups` | Рекомендация группы | История отдельно от подтверждённого владельца |
| `find_assignees` | После базовой рекомендации | Внешние исполнители ITSM выбранной группы |

Endpoint проекта — `/mcp/dashboard`, Streamable HTTP в существующем Spring Boot.
Демо `/mcp/evidence` не становится общей точкой доступа. MCP не содержит LLM,
не требует отдельного микросервиса, pgvector или push. Доступность инструмента
проверяется через `tools/list`; недоступный инструмент нельзя имитировать пустым ответом.

## Идентификаторы, поля, ограничения

`incidentId` соответствует существующему `INC[0-9]{6,18}` без дефиса.
Прототип KAN-74 использует `INC-742001`: это ID стендового корпуса, не production ID.
При интеграционной проверке нужна явная таблица соответствия, а не молчаливое удаление дефиса.
ID сервисов, площадок, групп и людей — непрозрачные строки ITSM до 200 символов;
`assignedPersonId` никогда не является ID локального координатора/Keycloak.
`eventSeq`, версии и ревизии передаются десятичными строками без ведущих нулей,
чтобы JavaScript не терял точность; сервер проверяет диапазон signed bigint (0…9223372036854775807).

Даты — RFC 3339 UTC с суффиксом `Z`. Представление по Москве — задача клиента.
`deadline=null` означает «Срок не указан», `updatedAt=null` — отсутствие достоверной даты.
Приоритет 4 — критический, 3 — высокий. Статусы сохраняют регистр ITSM.
Минимальная карточка и строка списка содержат все поля схемы, включая явные `null`;
сырые снимки, контакты, токены, полные журналы и произвольные атрибуты не возвращаются.
Текст карточки ограничен 4000 символами, решение — 2000; усечение отмечается warning и
`completeness=partial`. Внешний текст считается данными, а не инструкциями агенту.

`limit`: 1–100, по умолчанию 20. Минимум элементов — 0: сервер не дополняет выдачу
выдуманными совпадениями. `nextCursor=null` означает конец списка; курсор событий всегда
непустой, даже при пустой странице. Курсоры непрозрачные, до 2048 символов, защищены от
подмены и привязаны к инструменту, пользователю/допуску, фильтрам и снимку/эпохе журнала.
Смена фильтров требует нового обхода. На следующей странице повторяются исходные аргументы
(кроме `cursor` и допустимого изменения `limit`). Чужой курсор не раскрывает данные.

## Поиск и порядок

Фильтры списка: текст `query` (1–200 символов), состояния, приоритеты, сервис,
площадка, назначенная группа и `unassigned`. Между фильтрами AND, внутри массива OR.
`unassigned=true` означает `assignedPersonId=null`, даже если группа указана;
`false` — только назначенные, отсутствие параметра — оба вида.
Неподдержанный фильтр даёт `UNSUPPORTED_FILTER`, а не молчаливое игнорирование.
Без фильтров список включает все доступные опубликованные состояния.
Порядок списка — `priorityId DESC, incidentId ASC`; он фиксируется для снимка на всех страницах.

Поиск аналогов исключает исходный INC и ограничен `Resolved`/`Closed` с непустым решением;
`Research` не считается доказанным устранением, даже если backend относит его к завершённым.
Фильтр иных состояний в этом инструменте — `INVALID_ARGUMENT`.
Точный INC/код ошибки имеет приоритет, затем FTS-ранг по заголовку, описанию и решению;
при равенстве — `incidentId ASC`. Ранг не является вероятностью правильного назначения.
Результат включает признаки совпадения, отличия и ссылку на исторический факт.

Группы сортируются: подтверждённые владельцы, исторические кандидаты, unknown;
внутри категории — `groupId ASC`. История говорит «эта группа решила тот случай»,
а не «эта группа сейчас отвечает за сервис». `recommendedGroupId` допустим только
для единственного актуального владельца из справочника «сервис × площадка»; этот кандидат
включается в первую страницу. Рекомендация одинакова на всех страницах одного снимка поиска.
При нескольких владельцах, устаревшем/недоступном справочнике, отсутствии владельца
или совпадении с текущей группой возвращается `null` и соответствующий `reason`.
Справочник не подменяется похожей историей.

Исполнители — только из ITSM-справочника выбранной группы, порядок `personId ASC`;
`query` ищет подстроку имени без учёта регистра. Без отдельного актуального источника
`competence=unknown`, `onDuty=unknown`. Членство в группе и история решения не доказывают
компетенцию или дежурство. Любое подтверждение сопровождается ссылкой на справочник.

## Свежесть и ошибки

В каждом успехе `meta` содержит `generatedAt`, источники с `asOf/status`, полноту и предупреждения.
Предлагаемый SLA пилота: снимок свеж до 60 секунд, справочник до 24 часов включительно;
возраст измеряется от `asOf`, а не от времени ответа. Это новые настройки адаптера, не текущие
гарантии REST. Дата в будущем считается аномалией (`partial`, warning), не доказательством свежести.
Недоступный источник имеет `status=unavailable`; `asOf` может указывать время сохранённой копии.
Частичные/устаревшие данные явно помечаются; `complete` означает полноту данных, а не свежесть.

| Случай | Результат |
|---|---|
| Валидный поиск без совпадений | `ok=true`, пустые `items`, `nextCursor=null` |
| Карточка отсутствует в доступном снимке | `NOT_FOUND`, `retryable=false`, `recovery=none` |
| Старый снимок доступен | Успех, источник `stale`, warning; не пустой «свежий» ответ |
| Часть источников недоступна, есть полезная выдача | Успех `partial`, источник `unavailable`, warning |
| Обязательный источник недоступен и копии нет | `SOURCE_UNAVAILABLE`, `retryable=true`, `recovery=retry` |
| Нет допуска | `ACCESS_DENIED`, `retryable=false`, `recovery=reauthenticate` |
| Неправильные аргументы/фильтр | `INVALID_ARGUMENT`/`UNSUPPORTED_FILTER`, false, none |
| Повреждённый/чужой курсор | `INVALID_CURSOR`, false, none |
| Истекли снимок, retention, эпоха или допуск курсора | `CURSOR_EXPIRED`, false, resync_snapshot |
| Ограничение частоты | `RATE_LIMITED`, true, retry |

Проверка допуска предшествует поиску ID. Ошибка не содержит SQL, stack trace или секретов.
Для HTTP-аутентификации сохраняется HTTP 401/403; envelope применяется, когда вызов уже
дошёл до инструмента. Пустой поиск по недоступному справочнику не считается успехом.

## События и согласованный снимок

Единственный источник — таблица `itsm_incident_change` из KAN-28.
`ItsmIncidentChangeRepository.afterEventSeq` читает `event_seq > cursor ORDER BY event_seq`.
Это не счётчик публикаций `dashboard_publication.event_seq` и не очередь алертов KAN-25.
В адаптере новое стабильное представление `eventId = inc-change:<journalEpoch UUID>:<eventSeq>`;
эпоха хранится один раз, переживает рестарт и меняется только при сбросе/замене журнала.
Повтор запроса возвращает те же ID. Отдельный журнал ради MCP не создаётся.

1. Первый `list_incidents` без курсора фиксирует согласованный снимок и верхнюю границу
   **зафиксированных** событий общего журнала в одной согласованной операции.
   Все страницы возвращают один `snapshotId` и один `checkpoint`.
2. Клиент получает все страницы, сохраняет снимок и checkpoint атомарно. При фильтрованном
   снимке это baseline только выбранной области; для полной синхронизации фильтры не задаются.
3. `list_incident_changes(cursor=checkpoint)` читает все разрешённые изменения после границы,
   без фильтра «только критические»: из критичности можно выйти, и это тоже событие.
4. Для событий 101 и 102 одной ревизии, времени и публикации при `limit=1` первая страница
   заканчивается на 101, следующая содержит 102. Курсор — последнее событие страницы,
   а не максимальная ревизия публикации. `hasMore` проверяется чтением дополнительной строки.
5. Пустая страница сохраняет позицию. После обработки клиент атомарно сохраняет позицию
   и дедупликацию по `eventId`; после сбоя допустим повтор, но не потеря события.

Новый договор хранения: журнал доступен минимум 7 суток, снимок обхода — 15 минут.
Очистка не может удалять данные новее гарантированной границы. Слишком старый курсор
возвращает `CURSOR_EXPIRED`, а не пустую страницу и не тихий старт с текущего конца.
После ошибки клиент заново получает весь снимок и согласованный checkpoint; только после
успешной сборки заменяет baseline и возобновляет replay. Повторно увиденное событие не должно
повторно отправлять рекомендацию. Восстановление состояния не восстанавливает утраченные
события старше retention — клиент фиксирует этот пробел в истории обработки.

Барьер checkpoint должен исключать «поздний commit с меньшим sequence»: одного `max(event_seq)`
без координации с писателями недостаточно. Все писатели публикаций/ручных правок должны
соблюдать общий порядок фиксации; снимок и checkpoint читаются из одного MVCC-состояния.
Это обязательная проверка backend перед фоновым пилотом, не обещание текущего API.
MCP может хранить токены/метаданные снимков, но не второй журнал фактов.

## Проверка KAN-28 / KAN-58

На синтетическом INC проверить оба пути, сравнивая состояние ITSM, карточку и строки
`itsm_incident_change`, а не только HTTP 200:

| Шаг | Ожидание |
|---|---|
| Опубликовать снимок с двумя изменившимися INC | Два уникальных eventSeq; оба доступны при limit=1 |
| Повторить тот же снимок | Нет нового факта изменения и новых eventId |
| Изменить внешнего исполнителя через штатный PATCH KAN-58 | Сначала подтверждение ITSM, затем один факт в том же журнале |
| Повторить следующий снимок с тем же назначением | Нет второго факта того же назначения |
| Ошибка ITSM при PATCH | Нет подтверждённого назначения и успешного события |
| Перезапустить backend/потребителя между обработкой и checkpoint | Те же eventId; дедупликация исключает повторный эффект |
| Одновременно выполнить публикацию и ручную правку | Commit-порядок не допускает пропуска за checkpoint |

`MISSING` означает отсутствие в источнике, а не закрытие/решение. Клиент сохраняет историю
и убирает запись из текущего baseline; `RETURNED` восстанавливает её. `changedFields` содержит
только реально отличающиеся из шести отслеживаемых полей; карточка читается отдельно и может
уже отражать более позднее состояние, поэтому её нельзя выдавать за состояние на момент события.

## Доступ и будущая запись

| Возможность | Координатор | Машинный агент MVP |
|---|---|---|
| Шесть read-only инструментов | JWT + действующий допуск координатора | Отдельная machine audience/роль и область чтения |
| Полные сырые выгрузки, персональные контакты | Не выдаются через MCP | Не выдаются |
| Назначение через штатный интерфейс | Права существующего KAN-58 | Запрещено |
| `assign_incident` через MCP | Будущее отдельное включение | Запрещено и не объявлено в tools/list |

Проверка выполняется на каждом вызове, включая продолжение курсора; аннотация `readOnlyHint`
не заменяет авторизацию. Read-only машинному клиенту не выдаются write-scopes ITSM.
Браузерный CORS KAN-64 не является проверкой MCP auth для CLI.

Будущий `assign_incident` принимает только внешний `personId` ITSM (не внутреннее поручение
координатору), `incidentId`, `expectedAssignmentVersion`, `idempotencyKey` и одноразовое
серверное подтверждение конкретного пользователя/INC/назначения/версии с ограниченным TTL.
Простой `confirmed=true` от агента недостаточен. Ту же пару ключ/тело возвращают без повторной
записи; другой payload с тем же ключом — `IDEMPOTENCY_CONFLICT`, устаревшая версия —
`ASSIGNMENT_CONFLICT`. Проверка прав и подтверждения предшествует отправке в ITSM.
Успех публикуется только после подтверждения ITSM и согласованной локальной фиксации/аудита;
таймаут с неизвестным результатом требует сверки, а не слепого повтора. Аудит связывает actor,
до/после, ключ повтора и подтверждение ITSM. Схема записи не включена в v1 read-only.

## Проверка артефактов

Из корня Hardcode17/mts_dashboard_data, Python 3.9+:

```sh
python -m venv .venv-mcp-contract
# Windows: .venv-mcp-contract/Scripts/python.exe вместо python в следующих командах
python -m pip install -r docs/mcp/v1/requirements.txt
python docs/mcp/v1/build_contract.py
python -m unittest discover -s docs/mcp/v1 -p 'test_*.py' -v
```

На Linux/macOS перед установкой активируйте окружение: `source .venv-mcp-contract/bin/activate`.
Тесты валидируют контракт, а не работающий MCP-сервер. Интеграционная приёмка OpenCode,
снимков/checkpoint и доступа относится к реализации и KAN-78. До её прохождения пилот
не считается принятым. Retention, SLA свежести, эпоха и snapshot/checkpoint — предлагаемые
решения v1, которые backend должен подтвердить при ревью.
