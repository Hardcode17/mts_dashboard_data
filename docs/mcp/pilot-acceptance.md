# Приёмка пилота MCP — KAN-78

Статус: план проверки, не отчёт о запуске. Пилот не принят, пока не собраны наблюдаемые ответы и источники истины по шагам ниже. Документ не заменяет автоматизированную приёмку ITSM KAN-52 и не описывает разработку клиента, агента или UI.

Основание: [контракт v1](MCP.md), [схема](v1/contract.schema.json), [примеры](v1/examples.json), входные случаи и справочник [KAN-74](../../prototypes/routing-advisor/demo.json). Новые исходы и гарантии не вводятся.

## Границы

- Локальная проверка контракта и удалённый пилот OpenCode — разные проверки: первая не доказывает работу сервера, вторая не заменяет валидацию схем.
- Пилот read-only: `list_incidents`, `get_incident`, `list_incident_changes`, `find_similar_incidents`, `find_resolver_groups`, `find_assignees`. Запись, push и фронтенд-редактирование в объём не входят.
- Для фонового сценария нужны подтверждённые backend snapshot/checkpoint, retention журнала и общий commit-порядок. Это условия входа, а не доказанные свойства текущего API.

## ID и данные KAN-74

- В fixture ID записаны как `INC-742001`; контракт принимает `incidentId` по шаблону `^INC[0-9]{6,18}$`, то есть без дефиса. Молчаливое удаление дефиса запрещено: нужна согласованная таблица соответствия. До неё удалённый вызов по fixture ID невалиден — это разрыв, а не успешный тест.
- Fixture содержит названия сервисов, площадок и групп (`Wi-Fi`, `Ростов-на-Дону`, `Сетевая поддержка Ростова-на-Дону`), а контракт — непрозрачные `serviceId`, `siteId`, `groupId`. Что названия являются ITSM ID, fixture не подтверждает; равенство ID проверяется только после согласования таблицы. В отчёте фиксируются `name` и соответствующий `groupId`.
- Сценарий — стендовый `INC-742001`: Wi-Fi, Ростов-на-Дону, текущая группа «Сетевая поддержка Москвы». Поля приоритета в fixture нет; `priorityId=4` задаётся тестовым снимком, а не `demo.json`.
- `INC-741003` одновременно исторический случай и запрос с тем же ID. Как вход `find_similar_incidents` его брать нельзя без отдельного решения: исходный INC исключается, результат неоднозначен.

## 1. Локальный контракт

Вход: корень репозитория, Python 3.9+.

```sh
python -m venv .venv-mcp-contract
. .venv-mcp-contract/bin/activate
python -m pip install -r docs/mcp/v1/requirements.txt
python docs/mcp/v1/build_contract.py
python -m unittest discover -s docs/mcp/v1 -p 'test_*.py' -v
```

Наблюдаемый ответ: код 0; генерация не меняет `contract.schema.json` и `examples.json`; тесты принимают шесть примеров и отрицательные случаи. Источник истины — схемы, примеры и вывод тестов, а не этот документ. К MCP-серверу проверка не обращается.

## 2. Удалённый OpenCode

Вход: развёрнутый endpoint `/mcp/dashboard` (Streamable HTTP), URL и способ токена от владельца стенда, действующий допуск координатора или machine-роли на чтение. В текущем `opencode.jsonc` подключён только Atlassian; Dashboard MCP там нет, доступность endpoint не подтверждена.

1. Добавить remote MCP-сервер с URL вида `https://<host>/mcp/dashboard`, не коммитя URL и секреты. Выполнить `opencode mcp list` и авторизацию по инструкции OpenCode.
2. Запросить `tools/list`. Наблюдаемо: ровно шесть инструментов, схемы соответствуют `$defs.XInput`/`$defs.XOutput`; `assign_incident` отсутствует. Источник истины — сырой ответ `tools/list`, а не README.
3. Вызвать `list_incidents` с `{"limit":1}` без фильтров, затем `get_incident` с полученным `incidentId`. Наблюдаемо: `contractVersion="1.0.0"`, `ok=true`, `isError=false`, поля карточки и `meta` по схеме, `structuredContent` совпадает с JSON в `content`. Источник истины — ответ и `contract.schema.json`.
4. Без токена получить HTTP 401/403; с токеном без допуска — `ACCESS_DENIED`, `retryable=false`, `recovery=reauthenticate`, `isError=true`. Источник истины — HTTP-статус и envelope; пустой успех недопустим.

## 3. Фоновый сценарий

Вход: новый критический INC в согласованном тестовом ITSM; соответствие fixture `INC-742001` и `priorityId=4`, service/site — по таблице ID.

| # | Вход | Наблюдаемый ответ | Источник истины |
|---|---|---|---|
| 1 | `list_incidents` без `cursor` и без фильтров | `snapshotId`, непустой `checkpoint`, `items`, `nextCursor`; все страницы полного обхода сохраняют снимок | Ответ инструмента, схема; checkpoint привязан к снимку |
| 2 | `list_incident_changes` с `cursor=checkpoint`, `limit=20` | Событие `kind=ADDED` для нового INC, `incidentId`, `eventId=inc-change:<epoch>:<eventSeq>`; `changedFields` — только реально отличающиеся поля | `itsm_incident_change`, ответ; не `dashboard_publication.event_seq` |
| 3 | `get_incident` по ID из события | `state`, `priorityId=4`, `assignedGroupId`, `assignedPersonId`, `deadline`, `updatedAt`; карточка может быть новее события | Карточка ITSM и ответ `get_incident` |
| 4 | `find_similar_incidents` по тому же ID | Для `INC-742001` аналог `INC-741001`, `matchedSignals`, `differences`, `historicalResolverGroupId`; исход «Перезапущен контроллер…» не выдаётся за текущую рекомендацию | `demo.json`, решение `INC-741001`, ответ |
| 5 | `find_resolver_groups` по тому же ID | «Сетевая поддержка Ростова-на-Дону»: `responsibility=confirmed`, `evidence.kind=directory`; «Сетевая поддержка Таганрога»: `historical`; `recommendedGroupId` указывает на подтверждённого, `reason=confirmed_owner` | `owners`, `resolved_by` истории, ответ |
| 6 | Координатор открывает основание и карточку | Видны `reason`, `evidence[]`, `matchedSignals`, `differences`, `historicalResolverGroupId`; переход по `evidence.sourceRef` (`itsm:INC-741001`) открывает карточку через клиент | Ответы шагов 4–5; URL-переход контрактом не задан |

Шаг 5 обязателен: история говорит «эта группа решила тот случай», а не «эта группа сейчас отвечает за сервис». Совпадение `groupId` исторической и подтверждённой групп не доказывает владение; проверяются `responsibility` и `evidence.kind`.

## 4. Негативные кейсы

| Вход | Наблюдаемый ответ | Источник истины |
|---|---|---|
| Нет допуска | HTTP 401/403 либо `ACCESS_DENIED/false/reauthenticate`; данных нет | Контракт, ошибки доступа |
| Фоновый агент пытается писать | `assign_incident` отсутствует в `tools/list`; вызов неизвестного инструмента — ошибка протокола, не `ACCESS_DENIED` | `tools/list`, матрица доступа |
| `find_similar_incidents` для `INC-742006` | `ok=true`, `items=[]`, `nextCursor=null`; аналог не выдуман | `relevant_ids=[]`, ответ |
| `find_resolver_groups` для `INC-742006` | `recommendedGroupId=null`, `reason=no_owner`; история не подменяет владельца | `owners` без «Видеонаблюдение/Сочи» |
| `INC-742003`, Телефония × Ростов-на-Дону | Два владельца; `recommendedGroupId=null`, `reason=ambiguous_owner`; `INC-741007` остаётся историей | `owners`, ответ |
| `INC-742004`, площадка не указана | `recommendedGroupId=null`, `reason=no_owner`; `INC-741008` не становится владельцем | `site=null`, ответ |
| `INC-742005`, текущая группа совпадает с владельцем | `recommendedGroupId=null`, `reason=already_assigned`; `INC-741010` не рекомендация | `current_group`, `owners` |
| `find_similar_incidents` с `states:["Research"]` | `INVALID_ARGUMENT/false/none`; `Research` не доказанное устранение | MCP.md, рантайм-правило (схема это не запрещает) |

### Недоступный и просроченный справочник

Вход: тот же `INC-742001` и справочник `owners` с `asOf` старше 24 часов (просрочен) либо без доступной копии. Fixture такого состояния не содержит; нужен согласованный тестовый дубль или управляемое отключение источника, без правки `demo.json`.

Наблюдаемое требование: `recommendedGroupId=null`, ни одна историческая группа не получает `responsibility=confirmed`, в `meta.sources` видны `status=stale|unavailable` и warning, полезная история при наличии остаётся. Для просроченного справочника MCP.md обещает `reason=directory_stale` при успешном ответе; это проверяемо.

**Разрыв:** для недоступного справочника контракт допускает два представления: успех с `reason=directory_unavailable` (поле есть в enum) и ошибку `SOURCE_UNAVAILABLE` (обязательный источник недоступен, копии нет). Правило выбора не задано, в ошибке нет `reason`. Приёмка не должна молча выбирать один вариант: фиксируется фактический ответ и отмечается, что контракт не различает «нет справочника, но есть история» и «нет обязательного источника». Это блокирует однозначную оценку негативного кейса.

## 5. Повторы, рестарт и курсоры

| Проверка | Наблюдаемый ответ | Источник истины |
|---|---|---|
| Повторить публикацию того же снимка | Новых `eventSeq`/`eventId` нет; карточка и назначение те же | `itsm_incident_change`, ответ replay |
| Новый `list_incidents` после повтора | Новый `snapshotId` допустим; сравниваются факты и checkpoint, не идентичность снимка | MCP.md, ответ |
| Два события одной публикации, `limit=1` | Первая страница заканчивается на 101, `nextCursor` ведёт ко второй, вторая содержит 102; `hasMore` проверен дополнительной строкой | MCP.md, ответ `list_incident_changes` |
| Рестарт backend между обработкой и checkpoint | Те же `eventId`; дедупликация исключает повторную рекомендацию | Журнал, состояние клиента |
| Повторная доставка события | Один эффект на `eventId`, без второй рекомендации | Клиентская дедупликация |
| Истёкший курсор | `CURSOR_EXPIRED/false/resync_snapshot`; не пустая страница и не старт с текущего конца; затем полный снимок и новый checkpoint | MCP.md, ответ |
| Ручное назначение через KAN-58, затем идентичный снимок | Назначение видно в `get_incident`; событие с `changedFields=["assignedEmployee"]`; повторный снимок не даёт второго события | ITSM, журнал, ответы |

`MISSING` означает отсутствие в источнике, а не закрытие. `RETURNED` возвращает запись. `eventSeq` и версии — десятичные строки; `eventId` стабилен между рестартами.

## 6. Обязательно для MVP и что не блокирует

Обязательно: удалённое подключение OpenCode и базовое чтение; шесть инструментов в `tools/list`; допуск и отказ без данных; снимок + checkpoint + replay; запрет записи; согласованные ID service/site/group/INC; различение confirmed/historical; отсутствие выдуманного владельца; определённый исход недоступного справочника.

Не блокирует MVP, если пилот заканчивается просмотром рекомендации: качество семантики и FTS-ранга, push, `assign_incident` и запись из MCP, фронтенд-редактирование. Эти пункты проверяются отдельно и не выдаются за принятые.
