# План проектирования фронтенда

Рабочее место координатора MCC: React + TypeScript + Vite + Gravity UI.

Документ собран по whiteboard-схеме кейса МТС (дашборд, карточка инцидента, заметки по поведению) и бизнес-ТЗ. Задачи заведены в Jira, проект `KAN`.

## 1. Что строим

Фронт — **рабочее место дежурного координатора**, а не вторая ITSM.

Он должен отвечать на три вопроса:

1. Что требует вмешательства смены прямо сейчас?
2. Кто уже вовлечён и какой следующий шаг?
3. Что уже проверили и что осталось открытым?

ITSC остаётся источником истины по карточке, приоритету, статусу и назначению. Фронт показывает данные, считает представления и проксирует изменения через бэкенд.

## 2. Границы фронта

Фронт делает:

- показывает инциденты и четыре группы внимания;
- сортирует по времени обновления;
- показывает критическое событие и подтверждение «Увидел»;
- открывает детали, историю назначений и ITSC;
- даёт фильтры и сохранённые представления;
- обновляется по данным бэкенда.

Фронт не делает:

- не хранит официальный статус и назначение;
- не назначает исполнителя напрямую;
- не меняет жизненный цикл инцидента;
- не ходит напрямую в ITSC из браузера;
- не делает ML-предсказания в первой версии.

Если в макете есть «редактировать и переназначать», это делается только через backend-proxy с audit trail. Иначе получаем два источника правды.

## 3. Пользователи и сценарии

- **Дежурный координатор** — основной пользователь, работает за десктопом.
- **Смена** — смотрит общий экран, распределяет работу по параллельным авариям.
- **Следующая смена** — принимает контекст: что проверили, кого ждут, что открыто.
- **Исследователь причин** — после устранения пользуется историей и материалами.

Основной сценарий: пока смена ведёт первую аварию, приходит вторая критическая. Нужно заметить, оценить, передать конкретную проверку и не потерять первую.

## 4. Информационная архитектура

```text
/                         Dashboard: четыре группы
/incidents/:id            Полная карточка инцидента (deep link)
/groups/:preset           Сохранённое представление (опционально)
```

- Детали открываются **Drawer поверх дашборда**, чтобы не терять контекст.
- ` /incidents/:id` нужен для ссылок из мессенджера и ITSC.
- Фильтры и активная группа — в query string: `?group=critical&priority=P1`.
- Критическое оповещение — overlay поверх любого экрана, не route.

- Desktop-first: 1440–1920 px, минимум 1280.
- 1024–1280 — две колонки, меньше — список с фильтром по группе.
- Одна карточка может быть в нескольких группах. Это нормально: ID один, состояние общее.

## 6. Dashboard

### TopBar

- Название смены и пользователь.
- `Последнее обновление: 14:58` и индикатор свежести.
- Статус соединения: `live / polling / offline`.
- Ручное обновление.
- Переключатель темы, если поддерживаем dark.

### LeftRail

- Группы с количеством.
- Фильтры: приоритет, продукт, команда, статус, SLA.
- Сохранённые пресеты: «Моя смена», «Только P1», «Research».
- Кнопка «Настроить группы».

### Group grid

- Четыре группы: Критические, Требуют назначения, Исследование, Текущие.
- Заголовок, счётчик, сортировка по `updated_at`.
- Виртуализированный список карточек.
- Пустое состояние и ошибка загрузки не ломают остальные группы.

### Компактная карточка

- Бейдж типа и приоритета, цвет по типу.
- `INC-2048` и `P1`.
- Заголовок.
- Продукт или сервис.
- Статус.
- Ответственный или команда.
- SLA: осталось / просрочено / «Срок не указан».
- Последнее обновление.
- Признаки «критический» и «требует назначения».

### Сортировка и приоритеты

Базовый порядок на экране — многоуровневый и не зависит от выбранного фильтра:

1. **Приоритет:** P1 → P2 → P3 → P4.
2. **Внутри приоритета:** срок SLA по возрастанию. Просроченные и ближайшие — выше.
3. **Если SLA не указан или совпадает:** дата появления по возрастанию. Раньше появился — выше.
4. **При полном совпадении:** ID по возрастанию.

Критические (активный P1) всегда показываются выше остальных и не должны скрываться фильтром по умолчанию. Фильтр по группе сужает набор, но не меняет порядок.

Позже можно добавить пользовательскую сортировку по статусу, команде или продукту, но базовый порядок остаётся: **приоритет → срочность → дата появления**.

### Критическое событие

- Полноэкранный overlay.
- Номер, продукт, описание, срок, текущая команда.
- Кнопка «Увидел».
- Очередь: подтвердил A и B, пришёл C — C остаётся заметным и неподтверждённым.
- Гарантированное окно обзора после подтверждения (30 секунд — параметр).
- Повторное открытие того же INC может требовать нового подтверждения.
- Дедупликация по ID и версии события.

## 7. Карточка инцидента

Drawer или страница:

1. **Header**: ID, приоритет, тип, заголовок, статус, кнопка «Открыть в ITSC».
2. **Сводка**: бизнес-влияние, начало, длительность, SLA, ответственный или команда, последнее обновление.
3. **Сервисы**: список затронутых сервисов, владелец, критичность, последнее обновление. Если сервисов много — `+N` и раскрытие.
4. **История**: назначения, смены статуса, комментарии, время и автор.
5. **Действия**: подтвердить, перейти в ITSC, при наличии — редактировать или переназначить через бэкенд.
6. **Состояния**: loading, error, empty, stale data.

## 9. Данные и типы

```ts

type Status = 'new' | 'assigned' | 'in_progress' | 'research' | 'resolved' | 'closed'

  id: string
  name: string

}

interface AssignmentEvent {
  at: string
  from?: string
  to?: string
  author: string
  comment?: string
}

interface Incident {
  id: string
  key: string
  title: string
  description: string
  productName: string

  status: Status
  type: string
  team?: string

  businessImpact?: string
  slaDeadline?: string
  createdAt: string
  updatedAt: string
  affectedServices: AffectedService[]
  assignmentHistory: AssignmentEvent[]
  itscUrl: string
}
```

## 10. API

```text
GET  /api/incidents?groups=critical,needs_assignment&sort=updated_at
GET  /api/incidents/:id
POST /api/incidents/:id/ack
POST /api/incidents/:id/assign      // если разрешено, proxy в ITSC
GET  /api/groups/presets
PUT  /api/groups/presets/:id
GET  /api/snapshot/status           // lastUpdated, stale
```

Браузер не должен знать URL и токены ITSC. Только бэкенд.

## 11. Состояние и обновления

- **Server state**: TanStack Query или SWR. Кеш, refetch, retry, stale-while-revalidate.
- **UI state**: группа, фильтры, выбранный инцидент, очередь алертов — local state + URL.
- **Real-time**: опрос снимка каждые 5 секунд; стенд читает моковый источник.
- **Ack**: оптимистично, с откатом при ошибке.
- **Конфликты**: версия или ETag; не перезаписывать чужое назначение.
- **SLA-таймеры**: один общий `clock` на приложение, а не `setInterval` в каждой карточке.

## 12. Дизайн и доступность

- Семантические токены темы, без хардкода hex.
- Критичность дублируется текстом и иконкой, не только цветом.
- Контраст текста на красных и жёлтых плашках проверить отдельно.
- Keyboard: фокус, Esc закрывает drawer и modal, Enter подтверждает.
- `prefers-reduced-motion` для анимаций overlay.
- Тёмная тема: проверить карточки и SLA-бейджи.
- Проверить 1920, 1440, 1280 и 1024 px.

## 14. Открытые решения

1. Кто владеет `assignee` после передачи: ITSC или дашборд.
2. «Требуют назначения» — вычисляемая группа или workflow-статус.
3. Как считаем SLA: источник, паузы, часовой пояс, отсутствие срока.
4. Как показываем несколько затронутых сервисов и их владельцев.
5. Пресеты групп: per-user или общая смена.
6. Оповещения: общий экран, Email, SMS, push, Telegram, Mattermost, MAX, МТС Линк, МТС Notifica и мобильный хаб. На стенде используются моковые адаптеры.
7. Роли: координатор, наблюдатель, админ.
8. Демо: жёстко зашитый JSON или уже API.

Результат решения по пунктам 1–5 обновляется здесь и в `AGENTS.md`.
